# 按 V05 实施 R36S 二合一掌机：技术攻关与验收手册

版本：V0.2；日期：2026-10-31；需求依据：[gl二合一游戏机V05.md](gl二合一游戏机V05.md)，v0.5（2026-10-29）。配套设计见[13详细交付书](13_HANDHELD_BLUETOOTH_PLAYER_INTEGRATION.zh-CN.md)。本文件交给BSP、蓝牙、MCU、应用、结构和测试工程师，规定“先拿什么证据、怎么实验、怎样定位、什么算完成”。

本文没有实际执行板卡上电、蓝牙抓包、编译、改焊或下列测试。所有测试状态初始为**未测**；示例日志、目录、协议与命令用于后续实施，不代表本仓库已存在对应程序。原V05不修改，原有目标不因风险等级而自动降级。

## 1. 验收范围与优先级

**核心验收是同一台掌机、同一个模式物理键、同一套本机功放与扬声器：游戏模式播放游戏声音；蓝牙音箱模式接收手机等移动设备上酷狗音乐、汽水音乐等 App 的播放。** 手机负责运行音乐 App，掌机负责蓝牙接收、本机发声和相应界面。音乐接收与歌词接收分别验收，前者成功不能代替后者通过。

先做最小闭环实测：游戏本机发声 → 专用物理键切为音箱模式 → 配对/连接移动设备 → 酷狗音乐播放 → 汽水音乐播放 → 同一物理键切回游戏 → 游戏恢复发声。按 FR-1 默认长按 1 秒确认切换；每步记录声音来源、声卡占用、音量、切换时延、游戏数据和界面状态。来回切换不得混音、持续串音、爆音或因手机自动重连抢占游戏声音。V05 的游戏向外部蓝牙音箱发射另行测试，不代替本闭环。

本轮基线是现有R36S/RK3326/ArkOS改装，先原屏完成系统，再做4寸屏；不以前一轮量产替代SoC建议改变本轮开发对象。必须保留：无触摸、单TF、手机已有App推送P0歌词、游戏A2DP Source/手机A2DP Sink、2.4G双人、H8 DS3231、H9麦克风FFT、H10高优先级唤醒、H11环境温度、单RGB与表盘开放规范。

P1包括本地LRC、音乐律动、PC编辑器和AstroToo转换器，属于正式后续交付；P2 HFP允许按V05裁剪。4寸屏和USB线连PC U盘导入不是P2。降级界面或读卡器导入不代替对应主需求；闹钟须运行、待机、软件关机三态全部通过。

| 关卡 | 最先要证明的事实 | 不通过时的决定 |
| --- | --- | --- |

## 2. 共用测试档案与样机准备

### 2.1 每条记录必须包含

`需求FR/H → 测试ID → 样机/板/屏/电池/外设ID → 原卡/固件/MCU哈希 → 手机/OS/App/配置 → 操作条件 → 预期 → 实际 → 原始文件 → 通过/失败/未测 → 缺陷与负责人`。

状态分开写：资料存在、代码完成、编译通过、模块实测通过、合体通过。模拟输入只能证明解析/UI的一部分；不能替代蓝牙、ADC、RTC、唤醒和功耗测试。

### 2.2 基线操作顺序

1. 标记原卡、备用卡和样机；保存整卡、分区表、启动配置/文件与SHA-256，封存原卡。
2. 备用卡按原系统恢复，跑冷启动、显示/背光、全键/摇杆、FN、声音、充电/电量、存档与关机，保存录像和日志。
3. 在设备上使用现有工具只读取证。下面是将来在Linux终端执行的示例，**本次未执行**；命令/工具缺失记录缺口，不顺手安装或更换内核：

```sh
uname -a
getconf LONG_BIT
readelf -h /bin/sh
cat /etc/os-release
cat /proc/cmdline
cat /proc/partitions
cat /proc/asound/cards
cat /proc/bus/input/devices
ls -l /sys/class/rtc
ls -l /sys/class/udc
lsusb -t
```

4. 另记录真实声卡PCM/混音控制、ES和各模拟器启动/退出方式、显示设备/后端、进程所有者、启动服务/custom.sh位置和执行顺序。没有/proc/config.gz时向供方取.config，不猜配置。
5. H1/H2/H3/H4/H9先外接验证；电源键/常电/I²C测绘由硬件人员断电检查、按设计限流和示波器验证后进行。
6. 所有后续改动应用到可回退备用卡。需要改Image时同步确认模块、GPU库与rootfs配套；普通外设/换屏不无条件换内核。

## 4. R01：P0手机歌词的完整攻关步骤

### 4.1 取样，不先写死协议

准备至少一款目标Android手机及其实际音乐App，并加入第二手机/OS及一个对照App；iOS单列实测，不先宣布全部可用或全部不可能。记录App完整版本、歌词选项、权限/锁屏/后台状态、曲目版本、本地/流媒体来源和接收端固件。

确认参考播放器上出现的是当前曲目的真实歌词，并确认其数据来源，不是品牌文案或壁纸。此前视频关键帧没有证明这一点；已有视频观察不能替代本关卡。

[AVRCP规范](https://files.bluetooth.com/wp-content/uploads/dlm_uploads/2024/10/AVRCP_v1.6.3.pdf)与[BlueZ Media API](https://bluez.readthedocs.io/en/latest/media-api/)不提供通用标准Lyrics属性。标准AVRCP本身有相应Vendor Dependent封装，出现该名称不等于发现私有业务；候选包括私有扩展、Title复用或其他实际连接路径。SDK中名为“歌词”的函数也可能只返回歌曲信息。

### 4.2 设备侧采集和对照

先在可恢复原型上运行已准备好的诊断工具；命令只是示例，抓包限自有/获授权设备，日志留本地。不存在工具时进入环境准备任务，不把零输出解释为手机未发送。

```sh
bluetoothctl show
btmon --write ./bt-case01.btsnoop
```

同步记录BlueZ对象/属性与已知模块的原始输出；用日志客户端订阅PropertiesChanged并按实际API读取Track、Status、Position，必要时受控轮询。不要假设Position会每帧通知，也不要让两个进程同时争用同一AVRCP会话。

逐项做开/关歌词、播放/暂停、切歌、拖动、锁屏、后台、断连/重连，对比原始文本与媒体身份。如果只有Title变动，先证实它在当前App是否表示歌词，再实现适配；如果是未知PDU，记录长度/事务/编码/请求响应后评估协议栈补丁。HCI抓包可读性取决于实际链路与工具，不宣称每份抓包都能直接看到完整明文业务。

### 4.3 明确成功样例与接口

交付最小复现包：操作录像、手机/App版本、音轨/歌词的合法测试来源、原始事件/包、解析说明、会话/曲目键、文本编码、到达时间、是否含位置/时间轴、断连与重连行为。解析器至少分三层：传输适配→标准化事件→歌词模型；不得把协议直接写进9款表盘。

| 观察结果 | 下一步 | 保留的完成边界 |
| --- | --- | --- |
| 有逐行推送 | 实现arrival时基，清旧行/清会话，测声音到屏幕偏差 | 能接收当前行；没有整首时间轴就不虚构 |
| 有完整时标歌词 | 解析时间轴，按远端Position+单调时钟同步 | 逐段seek/暂停/重连验证 |
| 只有曲名/歌手 | 排查开关/能力协商/请求，或音频模块SDK | 不能勾选P0歌词；P1 LRC可单独验证 |
| 手机不发送/栈未暴露 | 分清发送端和接收端，选择栈适配或带原始歌词API的模块 | 不悄悄增加手机伴侣App或删FR-2 |
| 新版本App失效 | 固定已验证组合，记录回归与适配责任 | 支持矩阵收窄需产品确认，不称通用支持 |

设置样机齐备后5–10个工作日的首轮收敛评审，不承诺逆向必然完成。失败保持未完成；本地LRC和无词页面是V05兜底，不是P0等价实现。

### 4.4 同步测试要留三条时间线

记录远端媒体位置、接收/解析事件的单调时间、本机PCM呈现与UI绘制时间。对逐行推送和本地LRC分别测试；避免用“蓝牙连接已过秒数”做播放位置。Title逐行变化不等于新歌；真正换曲/会话变化才重置track_key。

原版/Live/翻唱/重名/多语言进入负样本；LRC匹配不确定应要求确认或显示暂无歌词。歌词误差阈值由实际通道评审冻结，未给定数值时保留待定项，不能伪称毫秒同步已达标。

## 5. R02/R03：双角色音频与安全切换

### 5.1 Source和Sink分两张证据表

- Source：同一核心先本机播放，再选外部蓝牙音箱，再静音；物理音量/静音、存档和游戏按键仍正常。主动断开音箱，验证自动回本地及安全音量。
- Sink：手机连接后本机发声，A控制手机播放/暂停，R2/L2调节；屏/耳机/麦克风同时工作。暂停PCM但手机仍在走不算AVRCP控制完成。
- 不在没有需要时启用并发转发或HFP。HFP关闭时来电由手机处理，不因收到来电强开通话profile。
- 控制器适配记录VID/PID、firmware、内核驱动与用户态库；RTL8761B候选不等于目标4.4 BSP已支持。位宽由实际rootfs/ELF/libc核实，不能固定写armhf或盲用arm64包。

主线采用与原ALSA链适配的[BlueALSA](https://github.com/arkq/bluez-alsa)。其当前与旧版命令名不同，固定版本再生成服务；如果选择其他后端，提交更改依据和全量回归，禁止多个服务抢同一PCM/profile。

### 5.2 每次切换是一笔事务

测试日志含request_id、from/to、按下时刻、长按确认时刻、存档请求/完成、PCM关闭、显示释放、蓝牙/路由准备、UI ready、提交/回退原因。连续按键只生成一次有效请求；重复请求幂等。

进入音乐前确认模拟器真实释放资源，不只停ES父进程；SIGSTOP不能保证PCM/DRM释放，kill -9不能保证存档。逐核心定义保存/退出适配，未支持时提示取消/保留游戏。回来时可先回ES加载存档，不能无证据宣称原游戏原位恢复。

2秒指标保留：同时报“按下→ready”“长按确认→ready”及存档等待；起算口径在评审冻结。超标写失败并分析保存/进程/蓝牙/显示哪段慢，不把配对时间和强制杀进程藏在统计外。全新配对、冷启动另记录，不冒充普通模式切换。

### 5.3 错误注入

在切换每阶段终止clock-ui、后端或模拟器，模拟MCU掉线、音箱断连、USB声卡拔出、卡满和重复按键。单一模式管理者恢复到能操作的游戏前端或安全故障页，最大重试次数与日志可查；不能无限拉起进程或丢失全部输入。

## 6. R04/R05：四USB设备与PC导入的实际验证

### 6.1 拓扑、电源和共存

H2、H3、H4（HID+CDC复合）、H9共4个物理USB设备；使用四下游以上合适Hub，不直接照“一拖三”。复合MCU在协议中有多个接口，但只占一个物理口。增加U盘等备用导入另计扩展。

测空载/典型/峰值/浪涌、5V升压余量、充电与Host供电角色、关机漏电和背供电。由硬件人员按已确认网络设计输入限流与测点，不提供未知主板的通用送电数值；不把充电口与Hub VBUS简单相连。

四设备全开时运行蓝牙/2.4G输入/采音/灯效/充电和最终壳体测试。检查2.4GHz共频、USB噪声和天线握持问题；不能在裸板上通过就认为内置必然稳定。

### 6.2 必须完成USB线连PC流程

先核实UDC、gadget驱动/configfs或其他目标版本实现、CC/ID、数据路径选择、VBUS检测/隔离。仅在/sys/class/udc看不到节点不等于SoC永远不支持，也不能视为已经能用；排查驱动/板级连接与供方资料。[Linux gadget配置说明](https://docs.kernel.org/usb/gadget_configfs.html)

`Host下停止业务并卸载导入卷 → 断开内部Hub数据路径 → 受控切Device并导出独立卷 → PC拷贝/弹出 → 解绑gadget → 本机校验与应用 → 恢复Host → 重枚举4设备/MCU握手 → 恢复业务`。

首选同TF上的专用FAT镜像卷或独立可卸载导入卷，不导出整卡/rootfs。按[Mass Storage Gadget文档](https://docs.kernel.org/usb/mass-storage.html)，导出期间本机不得另挂载/修改同一后端；即便外层TF数据分区仍挂载，镜像内部文件系统也必须只有一个所有者。不能一边用循环挂载读包，一边让PC写同一镜像。

测试Windows基础场景，以及最终宣称支持的其他PC系统；覆盖安全弹出、未弹出拔线、拷贝中断、写满、重复包、坏文件系统、断电/重启。恢复后原系统/存档不变，上一有效表盘保留，外设自动重连。读卡器/U盘备用可供调试，但T17仍要按USB线连PC验收。

导入中闹钟要响时保留PC卷所有权，不强制改Host；使用主机本地声卡/显示响铃，原掌机GPIO键处理停止/贪睡。导入退出后才恢复USB采集/接收器；若目标音频路径依赖被断开的USB设备则须修架构，不能丢闹钟。

## 7. R06：H8/H10 RTC到准点响铃的验证配方

### 7.1 测清“关机”是哪一种

按最新需求，运行、待机和软件关机均须支持已启用闹钟，覆盖游戏与蓝牙音箱模式，不受关机前模式限制。分别记录屏灭、suspend、SoC软关机但主电池连接、拔电池/运输断开。软件关机要求针对有常供电链且电量足够的状态；RTC备电不供SoC，不对完全断电承诺开机。H8按V05必配，调查原PMIC RTC只用于理解/比较，不能未经变更将DS3231删掉。

待机测试必须区分仅灭屏与真正系统挂起。进入挂起前设定并读回RTC事件，验证实际有效的硬件/内核唤醒路径，不能预设USB CDC支持唤醒。到点后记录唤醒信号、系统恢复、声卡就绪和首个铃声；同时验证游戏状态保留与手机连接处理。主机运行中不得误发开机脉冲，同一事件仅消费一次；覆盖临近响铃时进入待机/关机、取消/贪睡/改时后重新设定、RTC设定失败提示。

### 7.2 电气步骤

1. 断电测绘电源键/PMIC网络及地、常电/关断域，明确每节点允许电压/上拉/极性；取得原理图或带依据的逆向图。
2. 测人为正常短按/长按的波形及开机行为，作为MCU等效脉冲依据；不从另一主板抄毫秒值。
3. 外接H8/H10，验证RTC告警脚、MCU睡眠唤醒、隔离和键线脉冲，确认不会拉死按键/产生背供电。
4. USB VBUS消失后，确认MCU仍由批准的常电电源运行，RTC备电/告警与HID/CDC脱机行为符合预期。
5. 告警保持有效时只消费一次；主机ACK、标志清除、重排与异常重启不得产生反复开机。
6. 测整板常电电流，包含MCU、RTC模块LED/稳压/上拉、备用电源与隔离漏电；不能把芯片典型µA当整机结果。

[DS3231数据手册](https://www.analog.com/media/en/technical-documentation/data-sheets/ds3231.pdf)提供备电、开漏中断、两个硬件闹钟及精度温区依据，不提供R36S键线接法。精确器件/模块来源和后缀要核实；其温度寄存器不满足环境温度替代要求。

### 7.3 调度与时间步骤

配置≥3组用户闹钟，用软件计算下一次事件映射到可用硬件告警；不要求3组直接占3个硬件槽。覆盖每日/周一至周五/单次、同分钟多组、贪睡5分钟、取消、时区/夏令时和手动改时；工作日不默认等于联网法定节假日表。

启动time_valid=false直到RTC或有效手动设置确认；RTC失效时显示未同步、跳过闹钟并留下原因，手动对时后恢复本次运行。不能把无效RTC导致的上次旧时间作为正常时间。写RTC失败时单独显示不具备可靠关机提醒。

测冷启动分布和最坏时间，预唤醒T_wake与响铃T_fire分别保留；先启动等待T_fire，不能为追准点提前响铃。验收记录设定时刻/实际INT/电源脉冲/Linux就绪/首个铃声音频，产品评审冻结允许响铃偏差与missed策略；该阈值未定义就标待定，不能自己声称“同手机准点”。

## 8. R07/R08：真实FFT、温度和可视化指标

### 8.1 麦克风链

H9采集真实PCM→有界缓冲→窗口/FFT→频段/包络→带时间戳消息→UI绘制；RGB音乐律动消费相同数据。推荐参数为13中的起点，先查询声卡支持格式，记录实际采样率、窗长、hop、排队、UI频率和drop。

使用外部已知测试声音/脉冲或同步标记测“拾音→显示”；有条件用回采/示波器或高帧率录像组合验证，不能拿不带声轨的动画FPS推断端到端延迟。目标≤100ms、≥20fps保留；报告延迟最大值/分布与掉帧，不只给平均值。

负例包括：静默、静音本机后外界发声、耳机播放、说话、低音量/爆音、充电、USB重连、采集错误。环境拾音包含喇叭与周围声是正常物理现象，不能改成PCM直取以假充麦克风。默认不回放麦克风；P2通话另测回声和上下行。

### 8.2 H11环境温度

用精度和校准状态已知的参考仪器，在声明的室内温区、静置、游戏热机、边充边玩和正常握持状态记录偏差；远离SoC/PMIC/扬声器/电池热源并预留合适环境耦合。必要时换传感器/位置/隔热/标定，不把SoC/DS3231板温或0.1°C分辨率当±0.5°C准确度。

1秒采样为拟定计划；样本失联/陈旧用无效标记，不锁住旧值当实时温度。V05写“刷新周期≥1秒”，本版采用1秒而不自行解释成任意慢刷新。最终测试条件和误差边界须冻结。

## 10. R10/R11：4寸屏、续航、结构与更新

4.0寸屏是阶段6交付目标；查完整MPN、DSI/电源/复位/LED/FPC/命令和机械图，默认先640×480 4:3，采用480×480方屏需记录画面比例变化和评审。驱动IC同为ST7701或同族R36机型不保证模组兼容；不抄跨树phandle/供电，不直接覆盖其他系统启动配置。

相关DTS在仓库外临时目录构建，记录dtc版本、退出码、警告、命令、源文件/目标硬件、输出哈希，再反编译查目标节点；未编译不写通过。屏切换后必须重测触达、显示/背光、9表盘、歌词/FFT延迟、按键、音频/充电/USB/温升和续航，保留原屏恢复组合。

续航要求不取消：冻结基准游戏负载、音乐音轨/音量、亮度、RGB/外设、环境温度、同电池健康状态及截止策略，比较T_music≥0.8×T_game。测电池侧电压×电流/积分Wh与实际小时，不以不同电压侧mA直接相除；分别记录屏/Hub/BT/声卡/MCU/RGB与常电贡献。即使最终音乐续航优于游戏，也需实测，不先估计必然下降10%–20%。

空间/外观要同时容纳4寸、按键、灯光透光、麦克风开孔、天线与维修。V05“除了新按键无开孔痕迹”与拾音/透光/换屏开口产生冲突时，提交实物方案签样，而不是文档里同时承诺。未重新设计原屏/原壳限制时不承诺成品外观。

custom.sh位置和更新行为以目标卡实际文件为准；独立目录不能保证绝对不受OTA影响。测试更新/回退/坏包/断电/重启、版本迁移、蓝牙配对、表盘与闹钟保留及整卡恢复，第二名人员按发布说明完成一次全功能恢复。
