# 二合一掌机的技术瓶颈、需求假设审查与验证计划

版本：V0.1；日期：2026-10-30。对应[13 二合一落地方案](13_HANDHELD_BLUETOOTH_PLAYER_INTEGRATION.zh-CN.md)。依据包括本地四段视频的 32 个抽样帧、相关 JPG、用户聊天附图、[V05 需求评审稿](gl二合一游戏机V05.md)、Panel4/boot.ini 及本次查询的一手协议/项目资料。未执行硬件、音频监听、蓝牙抓包、移植、功耗或认证测试。

## 1. 结论：先查什么最能避免返工

二合一原理上可实现，应用显示与普通 A2DP 音频有成熟技术基础；但**当前尚不足以承诺“除换屏外全部低风险”**。阻塞完整功能的首要问题是无 Wi-Fi、无手机专用 App 条件下，目标手机音乐 App 究竟发送什么歌词数据，接收端能否稳定得到；其次是游戏切换时的资源/存档处理、关机闹钟的实际供电/唤醒路径，以及四个 USB 外设和单卡导入冲突。

先用外接原型和日志建立证据，再确定控制器/模块/Hub/MCU 和最终板卡。换屏独立后置；不能用成功收歌、滚动静态文字或一段表盘动画替代完整蓝牙歌词验收。

| 风险 ID | 瓶颈 | 当前等级/证据 | 必须先通过的门槛 |
| --- | --- | --- | --- |
| R-01 | 目标音乐 App 的歌词数据来源与兼容 | 高；标准元数据没有通用歌词字段，实际推送未经抓包 | 至少指定目标组合能收到真实歌词行/时间轴，并有原始记录 |
| R-02 | 原厂播放器并无已取得的可移植运行时 | 高；只有参考视频和 PC 编辑器来源 | 选择自研，或取得目标运行时、接口和适用授权 |
| R-03 | 软关机后 RTC/MCU/电源键唤醒 | 高；未测电源网络，当前没有电路与静态电流证据 | 断电域/电平/时序确认，软关机到响铃完整可复现 |
| R-04 | 游戏/音乐共享声卡、屏和按键 | 中高；直接停进程不能保证保存与资源释放 | 明确状态机、确认策略、音频所有者和异常回退 |
| R-05 | Hub 数量、电源与 USB 角色 | 中高；V05 三下游不覆盖四个 USB 设备 | 冻结 USB 拓扑、端口数、5V 预算、线缆与导入方案 |
| R-06 | 蓝牙芯片驱动、内核与 ABI | 中高；没有目标 VID/PID、固件和系统清单 | 指定板/镜像下枚举、收歌/控制、重连与日志通过 |
| R-07 | 单 TF 的存储一致性/更新 | 中高；根系统、游戏、主题与导入同卡 | 明确分区所有权，坏包/断电/恢复不破坏用户数据 |
| R-08 | 麦克风可视化、环境温度真实性 | 中；画面只能证明动态效果 | 采样和传感器实测；输出类别、误差与无数据状态定义 |
| R-09 | RF/2.4G 干扰、音质与续航 | 中高；未有合体测试 | 最终壳体下游戏/音乐/手柄/充电并存验证 |
| R-10 | 4.0 英寸屏与原厂表盘转换 | 高但可分阶段隔离 | 原屏完成功能，屏规格/驱动/资源边界和转换样例独立验收 |

这些等级是当前项目缺证据状态下的工程判断，不是完成测试后的失效率。

## 2. 最大瓶颈：蓝牙音乐、媒体信息、歌词是三层能力

### 2.1 必须拆开验收

| 能力 | 可以做什么 | 不能自动推出什么 |
| --- | --- | --- |
| A2DP Sink | 接收手机编码音频，解码后播放 | 能取到歌名、歌词、封面或完整播放时间轴 |
| AVRCP 控制/元数据 | 播放/暂停等控制，远端提供时可获曲目/状态/位置等 | 所有手机/App 都提供全部信息；存在标准统一歌词字段 |
| 歌词业务通道 | 对方确实发送且接收端正确适配时，可获取行歌词或完整时间轴 | 一定是私有命令、一定是完整 LRC、一定只支持 Android，或全 App 通用 |

[Bluetooth SIG AVRCP 1.6.3](https://files.bluetooth.com/wp-content/uploads/dlm_uploads/2024/10/AVRCP_v1.6.3.pdf)和[BlueZ Media API](https://bluez.readthedocs.io/en/latest/media-api/)是标准能力依据。标准属性里有 Track/Position，但不是现成的 Lyrics 服务；封面也有独立能力/版本要求，不是所有元数据实现必然具备。

### 2.2 不能先认定“所有手机歌词都是某种私有 vendor 命令”

实际待判定路径包括：①手机把当前歌词复用到标题等字段；②特定厂商/应用扩展；③额外控制/数据连接；④设备自己从本地文件取歌词。AVRCP 标准命令本身也使用相应的 Vendor Dependent 封装，抓包里出现该字样**不等于证明发现了私有歌词协议**。

杰理[公开蓝牙资料的检索内容](https://doc.zh-jieli.com/KDocs/master/音频技术应用文档入口汇总/蓝牙相关/)存在歌曲信息/“歌词”回调线索，[其 SDK 版本记录](https://doc.zh-jieli.com/AC792/zh-cn/wifi_video_master/other/version/index.html)也有歌词/图片转送相关记录。但不同 SDK/芯片/模块接口不同，名称本身不能证明能拿到手机逐行歌词，更不能证明 USB HCI 控制器 + BlueZ 可不经适配复用同一能力。

V05 关于“仅 Android、iOS 一定不可行”的结论不能直接作为设计事实：对某种私有扩展存在限制，不等于所有元数据复用或设备业务路径都被排除。反过来也不能承诺 iOS 可用；按具体手机/OS/App/版本/开关与接收方案测试。

### 2.3 最小取证实验

1. 选定用户实际使用的两款手机及其音乐 App/版本；另外加入一个无车载歌词能力的对照 App，记录手机本地/流媒体两类来源。
2. 如现有参考播放器可显示真实歌词，先用同一手机/App 复现并录像，确认不是演示文案、设备本地内容或联网插件。
3. 在路线 A 原型记录蓝牙能力、媒体事件与时间戳；可用时保存 `btmon` 等 HCI 日志及 BlueZ D-Bus 属性变化，记录哪条链路实际收到文本。只观察本项目自有/获授权测试设备，原始日志保留本地。
4. 分别开/关歌词选项，执行播放、暂停、下一首、拖动、锁屏、后台、断连和重连；比较 Title/Artist/Position 和相关数据是否变化。
5. 根据数据选择解析层：标准字段复用先用 Media API；确属未暴露扩展，再评估协议栈适配或路线 B 的模块 API。没有实际数据，不先投入长周期“逆向解析器”。
6. 形成可重复样例：原始包/事件、编码、文本长度、是否含时间、曲目身份、收到/播放/显示时刻、异常行为。失败明确卡在发送端、连接/协议层还是 UI。

候选收敛窗口为样机就绪后的 5–10 工作日，不是保证届时一定完成协议适配。若无结果，不能把 R-01 降为已解决；需采用证据充分的模块或变更覆盖范围。

### 2.4 兼容矩阵的最小字段

每行填：`手机型号 / OS版本 / 音乐App及版本 / 歌词开关 / 本地或流媒体 / 接收方案与固件 / 音频 / 元数据 / 行歌词 / 时间轴 / 暂停 / 拖动 / 锁屏 / 重连 / 原始证据 / 已知限制`。国内与海外 App 分别记录；不要把一款国内 App 测通写成海外手机通用。

歌词未取得时可显示曲目信息或匹配用户已有 LRC，但这是受限兜底。核心 P0 要求未调整前，不能因此宣布“手机蓝牙歌词完成”。

## 3. 歌词同步与媒体身份的工程问题

| 问题 | 需要实现的机制 | 验证方式 |
| --- | --- | --- |
| 推送只有当前行，无 LRC | 以行事件更新 UI，不伪造完整时间轴；失联/超时清理 | 暂停、拖动、快切歌，检查无旧行滞留 |
| 歌词复用 Title | 区分播放会话/曲目身份与文本行更新；不把每行变化都触发新歌 | 同一首连续更新与真正下一首对照，观察匹配/进度是否重置 |
| 本地 LRC 同名/不同版本 | 优先可靠媒体 ID；否则组合歌名/歌手/时长等并允许手动确认 | 原版/Live/翻唱/多语及重名曲，不误配或说明无法匹配 |
| 远端 Position 更新不连续 | 使用媒体时间锚点与单调时钟插值，状态变化/seek/重连后重新锚定 | 暂停不继续滚动、拖动后重新定位；不能只计算蓝牙连接经过时间 |
| 声音与文字不同延迟 | 区分收到文本、远端播放位置、本机音频缓冲和屏幕显示时刻 | 使用有时间标记的自有测试音轨，测偏移分布，不从视频估算协议延迟 |
| 多种语言/编码 | 支持明确编码与换行，限定超长文本，字体资源受控 | 中文、英文、重音/特殊字符、缺字与坏数据不崩溃 |

同步误差门槛应在拿到实际通道后冻结，并按“行推送模式”和“本地 LRC 时间轴模式”分别设定；不能把都叫蓝牙歌词当成相同精度保证。不得自动转用设备在线抓词或手机专用 App 规避当前无 Wi-Fi/无新 App 的要求。

## 4. 蓝牙硬件、内核和音频后端

蓝牙版本号、USB 外形与“支持 source/sink”的广告不能替代链路验证。先确认 Classic BR/EDR 和相关 profile、USB/UART 连接、驱动/固件及目标 BlueZ/音频版本；BLE-only 的模块不能直接承担经典 A2DP。RTL8761B 等候选的 VID/PID、固件与旧内核支持需要在目标卡测试，不能无条件写“4.4 内核现成驱动可用”。

[BlueALSA](https://github.com/arkq/bluez-alsa)适合以 ALSA 为主的专用设备；[PipeWire](https://docs.pipewire.org/page_man_pipewire-props_7.html)可管理音频图和蓝牙角色，但要验证依赖与原 BSP。选一条经过验证的后端，不把多个服务一起启用当兼容方案。BlueALSA 的现行组件名与旧版本也有变化，固定版本后才写启动命令。

交付清单：`uname/内核配置、CPU与rootfs ABI、libc/动态库、BlueZ/后端版本、控制器VID/PID或UART参数、firmware文件及来源、profile/codec、ALSA设备、日志与补丁`。SoC 支持 ARM64 不等于用户态全部是 arm64，也不等于必须 armhf；静态打包不能自动解决所有 D-Bus、音频和图形依赖。

游戏音频外发是 A2DP Source，与手机收歌的 Sink 方向不同。先采用两种产品模式互斥的连接策略；同时多角色/多连接若要实现必须另测。游戏蓝牙延迟随手机/音箱、codec、缓冲和后端变化，不把固定 100–200 ms 当产品保证；默认本地游戏出声更容易控制体验。

## 5. 模式切换：不丢存档、不抢资源

| 所有权 | 常见失败 | 工程对策 |
| --- | --- | --- |
| 游戏存档 | 强杀进程或立即断电，原生/即时存档未落盘 | 每核心定义退出/保存能力；用户确认；保存成功后才切换；失败保留原模式 |
| ALSA/音频 | ES 停了但模拟器仍持有声卡，或音乐后台继续出声 | 追踪真实进程和 PCM；先静音/停止并确认释放，再建立另一条路由 |
| 屏/DRM/framebuffer | 冻结进程仍占显示设备，画面黑屏/重叠 | 明确显示所有者和交接协议，验证目标 BSP；超时回退 |
| 按键/摇杆 | 两程序都读到按键；切换时残留按下状态 | 独立模式键、设备身份和输入仲裁；不要在游戏时独占整块手柄后丢弃游戏输入 |
| 崩溃与异常 | 反复切换生成多个播放器实例或失去全部输入 | 单一管理者、状态持久化/幂等、超时、看门狗与可诊断恢复 |

[Linux 输入事件文档](https://docs.kernel.org/input/event-codes.html)定义的是事件接口，不会自动实现全局热键、存档和模式隔离。优先独立 GPIO/MCU 设备作为模式输入，避免依赖容易与游戏重合的普通键码。

测试：菜单间往返 100 轮；游戏运行中保存/取消各多轮；音乐播放/暂停/断连时切换；故意结束 UI/后端进程后恢复。V05 ≤2 秒先作为管理者接受切换后到目标菜单就绪的候选，不把配对、存档等待和冷启动算成无条件 2 秒。

## 6. Hub、供电、USB Host/Device 和单 TF

**直接端口计算**：USB 蓝牙 + 2.4G 接收器 + HID/CDC MCU + USB 麦克风声卡 = 4 个下游设备。V05 的一拖三 Hub 不够；U 盘导入还需另加可用端口。改用 UART/GPIO/板载采集能减少 USB 数，但不是零工作量替换。

电源核对：Hub、蓝牙、接收器、声卡/麦克风、MCU/RGB 的典型/峰值/浪涌、5V 升压余量、线损、反灌和关机漏电；数据线完整性与结构固定另测。没有明确的限流/保护/电源路径前，不将两个 Type-C 口 VBUS 直接并联。

同一 OTG 控制器不能因为有 Hub 就同时既作 PC 的 USB Device 又作下游外设的 Host。若切到设备模式，原 Hub 和接收器可能断开；必须有数据路径切换和干净的外设生命周期管理。一个系统挂载中的分区也不能同时由 PC 作为块设备写入。

首轮用关机读卡器或 Host 下 U 盘导入，保留单 TF 架构。若需线连 PC，单独评审可卸载的数据分区/导入镜像、程序停用、USB 角色恢复与断线恢复。不能为了便利导出系统 rootfs，或在播放/游戏中同时让 PC 修改主题、歌词和存档。

## 7. 关机闹钟：RTC 能走时不等于能开机

V05 的 DS3231 作为保时器件有原厂依据，但**RTC → 关机后仍工作的控制/电源域 → 安全电平的唤醒 → SoC 启动 → 铃声**是另一条链路。[DS3231 数据手册](https://www.analog.com/media/en/technical-documentation/data-sheets/ds3231.pdf)给出开漏中断、备电和两个硬件闹钟等能力，不证明 R36S 的电源键可直接并接。

1. 先区分屏灭、系统 suspend、软关机后电池仍连接、拔电池/运输断开。RTC 备电只保障其自身，不能从硬断开的电源中凭空启动整机；只有明确具备供电链的状态才承诺唤醒。
2. 测量原板是否已有可用 PMIC RTC、备电和唤醒接口，再决定 DS3231/MCU 接法；本轮 DTS 中未找到显式 rtc 文本不等于 PMIC 驱动不会注册 RTC。
3. 查电源键网络、电平/极性、按压时序、关机后上拉和常供电域。USB 总线供电 MCU 随 Hub 掉电后不会自动常驻；如需常电，重新设计稳压、漏电、反灌与 MCU 唤醒。
4. 开漏/隔离只是候选拓扑，不给未知网络直接飞线。根据器件上限、原板电路和测量确定电平转换、脉冲、供电与故障行为。
5. 持久化至少 3 组软件闹钟，但 DS3231 只有 2 个硬件闹钟，软件需调度最近事件、处理重复/工作日/贪睡、RTC 失效/改时与时区，不能一组需求直接对应一个硬件槽。
6. 记录最坏冷启动时间；要在 T 点响铃，应评估 T−启动裕量预唤醒或常电小音源路径。开机才发现闹钟已过点，不能声称“关机准点提醒”。
7. 流程验证：写入/读回 → 安全关机 → 测 RTC INT 与唤醒 → 开机识别原因 → 铃声 → 清标志并重排，检查没有重复开机和持续耗电。

DS3231 的 ±2 ppm 条件、温区与器件变体应按精确型号核对；其内部温度值不等于环境温度。RTC 模块自带 LED、稳压、上拉及 MCU 常供电可能使整板电流远高于芯片典型值，V05 的“µA 级”须整机实测后填写。

## 8. 麦克风、声音效果与环境温度

麦克风环境拾音可做波形/包络/FFT 可视化，但本机播放音乐也会进入麦克风，因此显示的是混合声场，不是隔离的原始歌曲频谱。根据产品目标分别提供“环境声”与“音乐音频”模式；后者可从解码 PCM 分析，属于另一路数据来源，不能静默替代要求的麦克风功能。

测试必须包括：扬声器静音时外界发声、耳机播放、不同距离/音量、安静环境底噪、充电/灯效/2.4G 干扰和采集失败。默认可视化不把麦克风回放到扬声器，以避免反馈；HFP 若做，增加全双工、回声消除、来电路由及隐私指示，不能因已有麦克风就称免提完成。

环境传感器应远离 SoC、PMIC、功放和掌心热源，评估透气、响应时间、静置及边充边玩偏差。SHT30/AHT20/LM75 各完整型号的标称范围不相同，不能一概承诺整机 ±0.5°C；分辨率 0.1°C 也不等于准确度 0.1°C。标定/热隔离不足时按实际误差显示或调整规格。

喇叭/腔体、功放/codec 增益、噪声与限幅决定音箱效果，小掌机不能只加蓝牙就达到参考桌面播放器的声学指标。额外功放/电池/孔位会改变结构、供电、温升和认证，须按实物比较。

| “无 RTC 电池”说明必须完全新增 RTC | 主板 RTC 驱动、备电与唤醒线路尚未核实 | 先检查 `/sys/class/rtc` 等实际运行结果及原理图/实测，不能仅凭照片判断 |
| MCU 经 USB 又能关机 µA 常驻 | USB 供电与常电不是同一电源域 | 明确常供电与隔离，测整机静态电流 |
| 关机闹钟是纯软件 | 软关机后 Linux 不运行，且有启动时间 | 硬件唤醒和软件调度两项分别验收 |
| 单灯功耗忽略、续航下降≤20% | 尚无模式、音量/亮度/音轨与电池侧测量 | 列电源预算，分别测纯游戏、音乐、闹钟待机，候选指标再冻结 |
| 固定交叉编译 armhf 并全部静态打包 | 用户态 ABI 和动态依赖未知 | 用目标镜像与工具链核对，不从主控位宽推断 |
| custom.sh 防所有 OTA 覆盖 | 实际钩子路径、执行时机和更新行为未核实 | 查真实固件文件/服务，更新前后测试，维护受控包与恢复路径 |
| 4 寸同源机 DTB 可以照搬 | 同系列、同接口或同芯片不代表同屏与同电源 | 取准确屏料号/电气/命令，独立适配和回归 |
| 原厂 480×480 JSON 可天然直映射 | 控件语义、字体、图片、动画和运行时未证明可重用 | 自有 schema；取得合法样例后逐控件转换，不承诺原包即插即用 |
| “表盘调研已入库” | 当前仓库检索未找到所引用的《Divoom表盘JSON调研.md》 | 不把缺失笔记作已验证证据，后续补确切文件/导出样例 |
| 无开孔痕迹，但又需麦克风/RGB/大屏 | 空间、拾音、透光、屏窗和天线需求可能冲突 | 明确外观允许改动，在手板评审时共同冻结 |

以上审查不擅自修改用户 V05，不取消已要求功能；把未经验证的实现假设转成有负责人和退出条件的任务。

## 11. 表盘移植、合规与供方交付边界

[Divoom 编辑器 README](https://raw.githubusercontent.com/DivoomDevelop/divoom-watchface-visual-editor_AstroToo/main/README.md)面向其原厂设备/资源，包含 LAN/云代理相关功能；本项目无 Wi-Fi，不能原样照搬上传路径。当前没有取得目标掌机播放器运行时和完整复用授权，应自研渲染/数据接口，或向原厂获得明确交付。自有表盘包也要记录字体、图片、动画和歌词内容的使用来源。

无 Wi-Fi 仍有蓝牙和 2.4G，无线、电池、EMC、地区参数及维护任务按[10 落地手册](10_PROJECT_PROCUREMENT_PILOT_EXECUTION.zh-CN.md)重新评估。蓝牙产品还需按 [Bluetooth SIG 官方资格流程](https://www.bluetooth.com/develop-with-bluetooth/qualify/)核对产品/设计使用与资格要求，不能把模组既有记录自动当成本品牌成品全部手续；这些与 FCC/CE/国内无线要求分别管理。

向蓝牙/板卡供方索取：准确型号、接口/供电/天线资料、目标 BSP/firmware、实际手机/App 矩阵、**逐行歌词与播放时间的原始输出示例**、编码/长度/错误定义、控制与音频接口、断连/重连、SDK/协议修改和再分发范围、维护与量产变更承诺。让供方拿测试曲和手机演示，不接受只展示歌曲名称。

## 12. 阶段决策与当前缺口

- 可立即推进：第一步掌机基线、单卡恢复、接口/空间测绘、无触摸 UI 原型、自有 schema、手机矩阵、外接收歌/歌词试验、RTC/电源键测量。
