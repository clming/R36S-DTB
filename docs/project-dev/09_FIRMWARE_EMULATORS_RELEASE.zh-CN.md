# RK3326 掌机：固件工程、模拟器集成与恢复发布方案

版本：V0.1；日期：2026-10-29。目标是交付可追溯、可维护、能恢复到指定硬件配置的整机软件，而不止复制一个 DTB。技术背景见[启动文件清单](05_RK3326_LINUX_SOURCE_BOOT_FILES.zh-CN.md)及[boot.ini 与模拟器说明](04_CHIPS_BOOT_EMULATORS_GAMES.zh-CN.md)。本文所列新工程目录、脚本、配置和发布物是**待实施交付**，本仓库当前没有整机 SDK；本次未安装工具、编译或烧录。

2026-10-29 更新：本文件 RK3326 启动链保留作原机研究示例；新产品按[11 替换方案](11_RK3326_REPLACEMENT_STRATEGY.zh-CN.md)重新选 BSP、boot/rootfs 和图形栈，不复用旧 Image/uInitrd/DTB 组合。海外本地化、安全维护和分地区发布任务见第 11 节，法规时间和适用性见[10 手册第 13 节](10_PROJECT_PROCUREMENT_PILOT_EXECUTION.zh-CN.md#13-国内与海外销售的新增工作包2026-10-29)。

## 1. 先固定一个能解释清楚的基线

首轮基线为“一块已知 PCB + 一个屏料号 + 一种电池包 + 一张系统卡 + 一份完整固件”。给它一个项目内部配置 ID，例如 `RK3326-HH-A01-P01`；示例 ID 不是已存在的硬件型号。新屏/新 DDR/新板版本分别管理，不靠颜色、月份或根 `model` 判断兼容。

| 路径 | 具体用途 | 开始条件 | 退出条件 |
| --- | --- | --- | --- |
| 原机/供方镜像复现 | 保存体验基线、查实际文件和模块 | 有原卡、备份卡和版本资料 | 能解释实际加载链，并在备用卡复现基本功能 |
| 既有发行版适配 | 快速验证板卡与模拟器 | 维护者列出对应硬件组合，逐组件审查使用范围 | 首版用例通过，已知限制/来源与恢复路径完整 |
| 自建可控固件 | 产品长期维护和裁剪 | BSP、工具链、库和组件资料可取得 | 第二人在记录环境中构建并恢复，功能与许可交付完整 |

产品首版可先用受控供方系统验证，再并行补齐构建；正式版本不能长期依赖未知来源的二进制拼装。

## 2. 各层源码和输出的确切分工

| 层 | 参考来源 | 应取得/生成的文件 | 必须配套核对 |
| --- | --- | --- | --- |
| DDR/前置固件 | 供方 BSP、[Rockchip rkbin](https://github.com/rockchip-linux/rkbin) | 按实际启动方案需要的初始化/安全固件 | SoC、DDR、布局、版本与分发条件，部分是二进制 |
| U-Boot | [Hardkernel U-Boot 分支](https://github.com/hardkernel/u-boot/tree/odroidgoA-v2017.09)或供方工程 | 平台引导产物、配置、布局与恢复说明 | 不猜写卡偏移；不与其他方案 loader 随意拼接 |
| Linux 4.4 BSP | [hardkernel/linux：odroidgoA-4.4.y](https://github.com/hardkernel/linux/tree/odroidgoA-4.4.y) | `Image`、DTB、所需模块 | 这是同 compatible 的源码起点，不是原卡确切构建来源证明 |
| initramfs | 所选发行版/自建 rootfs 工程 | 本方案若需则提供 `uInitrd` 或其他实际命名 | 文件名不能证明 U-Boot 头和压缩格式；依目标加载器验证 |
| rootfs | 供方可构建系统或 [Buildroot](https://buildroot.org/)工程 | init、库、模块/固件、音视频栈、程序和默认配置 | 用户态 ABI、内核接口和 GPU 驱动组合 |
| 前端 | [EmulationStation 上游](https://github.com/Aloshi/EmulationStation)或选定受维护分支 | 平台列表、主题、启动命令、输入与设置 | 照片只确认家族，实际分支需从原机提取确认 |
| 模拟器 | [RetroArch](https://github.com/libretro/RetroArch)、[mGBA](https://github.com/libretro/mgba)、[PPSSPP](https://github.com/hrydgard/ppsspp)等 | 主程序、libretro 核心 `.so` 或独立程序 | 每组件版本、架构、依赖、配置和许可 |
| 完整镜像 | 项目固件打包工程 | 包含引导区域/分区/文件系统的 `.img` 和校验 | 不把复制 BOOT 文件当成生成完整系统 |

当前网络候选发行版和固定版本的具体下载入口集中保留在[05 文档](05_RK3326_LINUX_SOURCE_BOOT_FILES.zh-CN.md)和[03 文档](03_FAST_DEVELOPMENT_PLAN.zh-CN.md)，避免多份文档各自更新成不一致的镜像组合。

## 3. 原卡取证和可恢复基线

1. 给卡和样机编号，保存整卡镜像、分区表、可读启动文件及哈希。原卡封存，后续只用备用卡；Linux 分区内容不能因 Windows 不显示就判定为空。
2. 在可用样机上记录内核、挂载、系统架构、输入和声音信息。可用时只读执行 `uname -a`、`cat /proc/cmdline`、`cat /proc/partitions`、`mount`、`cat /proc/bus/input/devices`、`cat /proc/asound/cards`。这些命令不会提供全部构建来源。
3. 若有 `/proc/config.gz`，保存内核配置；没有时向供方申请，不通过猜测 defconfig 宣称可重现。
4. 找到实际 U-Boot 加载配置，记录 Image/initrd/DTB 文件、分区和地址；`boot.ini` 在目录里存在不代表被执行。
5. 记录 `/lib/modules/`、库架构、图形后端、前端启动服务/脚本、核心路径、ROM/BIOS/存档路径与权限。扫描清单避免对外发布用户私有内容。
6. 用完整备份在备用卡恢复，按[验收 AT-01～15](06_PRODUCT_BASELINE_AND_ACCEPTANCE.zh-CN.md)记录结果。只读清单通过不等于已成功恢复。

## 4. Linux 工程与构建交付怎么做

Hardkernel 分支的已核实参考目标为 `odroidgoa_defconfig`、`rk3326-odroidgo3-linux.dtb`，固定源码记录见[05 第 1 节](05_RK3326_LINUX_SOURCE_BOOT_FILES.zh-CN.md)。先取得供方使用的工具链、主机依赖、补丁和完整配置；旧 BSP 不承诺可直接使用当前系统默认 GCC 编译。

| 构建步骤 | 工程人员操作 | 应保存的证据 |
| --- | --- | --- |
| ENV | 在单独 Linux 构建机/受控环境准备依赖，冻结版本 | 主机/工具链版本、镜像或环境说明、资源需求 |
| SRC | 取完整仓库、固定 commit 和补丁，不只下载一个 DTS | remote、commit、补丁、全部子依赖与哈希 |
| CFG | 以已核实 defconfig 起步或采用供方完整 `.config` | 配置差异、驱动、模块和 ABI 说明 |
| BUILD | 通过内核构建系统生成 Image/DTB/modules | 完整命令、退出码、警告、日志和输出清单 |
| STAGE | 模块安装到临时 rootfs staging，禁止直接改目标卡 | kernelrelease、模块版本/依赖、staging 清单 |
| VERIFY | 检查 DTB、Image、实际启动路径，再在备用卡测试 | 哈希、反编译节点、启动日志与用例结果 |

ARM64 内核输出通常位于 `arch/arm64/boot/Image`，对应 DTB 位于 `arch/arm64/boot/dts/rockchip/`；独立输出目录时应按构建设置定位。安装模块还要带匹配版本目录、依赖信息和必要固件，不只复制 `.ko` 文件。

[ArkOS 相关 rg351 README](https://github.com/christianhaitian/linux/blob/rg351/README)明确限定 RG351 设备，记录工具链、Image/DTB、模块及匹配 libmali 的工作。这是配套关系的直接例子，不应照搬它的 defconfig 给新 R36S 板，也不把其历史依赖安装命令当作本机已执行操作。

## 5. 设备树适配工作清单

| 改动 | 工程工作 | 完成证据 |
| --- | --- | --- |
| 换屏 | 实际屏规格→DSI/复位/电源/命令/时序/背光→驱动支持 | 命令来源、时序计算、dtc 输出、实机图案和长时间测试 |
| 换 GPIO/按键 | 原理图/pinmux→GPIO 控制器/有效电平→事件码→热键 | 逐键日志及前端/全部首发核心测试 |
| 换摇杆 | 量程、多路器/ADC、通道/方向、校准/死区 | 四轴原始值、回中/边界及装壳测试 |
| 换电池/供电 | 电芯和 PMIC 依据→参数/调节器/USB→低电策略 | 电源审查、充放电/温升及关机记录 |
| 换音频 | I²S/codec/负载/检测线路→DTS→混音配置 | 喇叭/耳机、充电噪声和插拔测试 |

新板建议在对应内核源码内维护可读的板级 DTS/DTSI，用符号引用和原厂 binding 表达网络。对当前反编译式 DTS 不做全局重排；数字 phandle 必须追踪本树引用、`__symbols__`、端点和 `native-mode`。Panel4 当前引用问题见[08 文档](08_ELECTRONICS_SCHEMATIC_BRINGUP.zh-CN.md)，不得无验证发布为新板配置。

编译先写到仓库外临时目录；带 include/宏的内核 DTS 用其构建系统处理。保留警告，不默认 `dtc -f`；输出反编译后核对目标节点，并记录 dtc 版本、命令、源文件、哈希和实机范围。当前 D:\GitHub\dtc 为已有工具来源目录，是否具备可执行文件需按[已有工具分析](../PANEL4_DTS_KERNEL_ANALYSIS.zh-CN.md)核查；本任务没有安装或重新编译工具。

## 6. 把模拟器变成产品功能

首版从 mGBA 等明确选定核心开始，再按平台逐个增加。不能用 Android APK、桌面 Windows 程序或其他 CPU 架构二进制替换 ARM Linux 构建；即使都是 ARM64，也要匹配 glibc/musl、图形和音频依赖。

| 工作包 | 具体内容 | 验收条件 |
| --- | --- | --- |
| SW-APP01 程序打包 | 为每个程序/核心建立配方、固定版本、依赖和哈希 | 在目标 rootfs 启动无缺库、无未知下载依赖 |
| SW-APP02 启动命令 | 每平台定义程序、核心、ROM 参数、工作目录及配置 | 中文/空格文件名正确传参；不把文件名拼成 shell 命令 |
| SW-APP03 输入 | 同一物理键在前端、RetroArch 和独立模拟器的映射 | 每个平台运行 AT-05～07 |
| SW-APP04 图形声音 | 选择与 BSP 匹配的 DRM/KMS、EGL/GLES、ALSA 等实际后端 | 记录初始化日志和实际性能；无音频持续断裂 |
| SW-APP05 保存 | 明确用户可写目录、权限、同步和版本兼容策略 | AT-08、正常关机和恢复后存档可用 |
| SW-APP06 异常回收 | 启动失败、缺 BIOS、损坏内容、进程退出返回前端 | 不留黑屏，不丢输入，错误可诊断 |
| SW-APP07 设置 | 统一亮度/音量/语言与默认值，保留用户设置 | 重启保持，恢复默认不清空内容 |
| SW-APP08 离线 | 首次启动、列表、运行和保存均不强制联网 | 断网完成完整使用流程 |

目录合同由固件团队冻结：系统程序/核心为受控文件，用户内容、存档、元数据和日志可写且分别管理。具体路径按所选发行版确定，不假定所有系统都使用 `/roms` 或同一种 TF2 挂载机制。

## 7. 游戏与 BIOS 的交付合同

游戏来自独立内容文件，不会因为安装模拟器而自动获得。建立 `内容ID/来源URL或合同/权利人/可商用与分发范围/文件哈希/平台/核心版本/必要BIOS/测试片段/存档版本` 清单。BIOS、封面、字体、主题、开机素材分别审核，不由 ROM 授权自动覆盖。

商用版本以自有/获授权演示内容作为最小交付，不把原卡几千个游戏直接复制到发布镜像。街机内容需核对 ROM set 与核心版本匹配；文件同名不代表集合内容符合要求。

[Libretro 官方许可索引](https://docs.libretro.com/development/licenses/)列有非商业条目；以固定提交的实际 LICENSE 和权利人批准为准。RetroArch 的许可不自动覆盖全部核心和游戏。保存源码、补丁、许可声明与所需提供方式；具体分发义务由项目合规负责人逐组件确认。原仓库 README 的 CC BY-NC-ND 4.0 声明保留，不能把公开可读当作整个仓库任意商用授权。

## 8. 打包、版本和恢复发布

建议另建整机固件工程，维护板级配置、内核/U-Boot 配置和补丁、包配方、rootfs 默认配置、镜像布局、测试及许可清单。可参考 [Buildroot 官方手册](https://buildroot.org/downloads/manual/manual.html)与 [genimage 官方项目](https://github.com/pengutronix/genimage)；二者都不自动提供本掌机全部适配。

| 发布物 | 必含内容 | 审核人 |
| --- | --- | --- |
| 完整系统镜像及校验 | 精确机型/PCB/屏配置、镜像大小、SHA-256、卡容量要求 | BSP+测试 |
| 软件 manifest | loader/U-Boot/kernel/rootfs/前端/核心/库的版本和来源 | 软件负责人 |
| 硬件 manifest | PCB/BOM/屏/DDR/电池/DT 配置 ID | 硬件+采购 |
| 恢复说明 | 备份、工具来源、物理卡识别、写后校验、首次启动和回退 | 测试+售后 |
| 许可和源码交付 | 逐组件 LICENSE、修改、适用的源码/获取方式 | 发布负责人 |
| 验证报告 | 全部 P0、性能、恢复、已知问题和不支持组合 | 测试负责人 |

`boot.ini` 中的 `root=`、UUID、地址、文件名以目标系统为准；本仓库是参考模板，不能整份覆盖。该模板加载 Image、uInitrd、rk3326-r35s-linux.dtb；外部 initrd 对此启动方案需要，但不是所有 Linux 系统的普遍必需文件。

刷卡采用已评估的成熟工具，例如 [balenaEtcher 官方项目](https://github.com/balena-io/etcher)。只对明确识别的备用卡操作，整卡写入会覆盖该卡内容；先备份、核对容量和目标、写后校验，再实机验收。普通换屏只改经确认的必要配置，不无条件更换 Image；确需换内核则连同模块和图形依赖做受控回归。失败时关机恢复本轮原文件，无法确认配套时换回封存原卡。

发布前第二人在独立环境按文档构建/恢复。若只证明重新构建可运行，应称“功能可复现”；只有实际哈希比对和构建条件验证过，才称“字节级可复现”。

## 11. 国内外软件底座、维护与发布增量

### 11.1 新平台的工程边界

H700/A133/RK3566/RK3568 使用各自实际引导、内核、DT、图形库与模块；即使输出名叫 Image，也不是 RK3326 的可替换副本。Android ODM 另交付分区/打包、系统签名、输入与音频、设置、升级和恢复，不默认包含 Google 服务授权，也不默认由当前 EmulationStation/Linux 配置直接迁移。具体来源入口见 11 文档。

### 11.2 可下发软件任务

| 任务 ID | 工作内容 | 完成证据 |
| --- | --- | --- |
| SW-EX01 共同源码 | 公共功能同源；市场差异使用受控配置；manifest 加地区/语言/RF/内容 ID | 国内/海外镜像差异清单与一键构建的实际记录，当前尚未实现 |
| SW-EX02 本地化 | 中英文与目的国语言、字库/译文许可、长文本、特殊文件名、语言切换和键义 | AT-17/18 全操作流；翻译审核不只检查主菜单 |
| SW-EX03 低依赖启动 | 无网络/无账号/无内容卡仍可菜单与恢复，时间错误不导致本地游戏不可用 | 离线首次启动、跨时区和错误时钟场景；联网服务可明确关闭 |
| SW-EX04 默认安全 | 禁用未批准 SSH/Telnet/Web/调试 ADB 等；批准服务按设计鉴权，无通用远程口令 | 实际启动服务/端口清单、安全扫描和工厂恢复后复核 |
| SW-EX05 更新恢复 | 包来源验证、硬件/地区/版本兼容校验、低电/坏包/中断处理、保留存档的恢复路径 | AT-21；清楚区分用户可回退版本与需修复的安全版本策略 |
| SW-EX06 漏洞维护 | 固定依赖与 SBOM、漏洞跟踪/分流、修复与报告责任、支持期和密钥保管 | 已签定人员/预算/流程；旧 BSP 安全修复能力不过关则回到平台评审 |
| SW-EX07 隐私诊断 | 用户主动导出版本/硬件/错误，不默认上传 ROM/BIOS/存档/密钥/个人目录 | 数据字段、告知/清除流程、日志脱敏和模拟售后记录 |
| SW-EX08 无线区域 | 固件/驱动/国家配置与已验证 SKU 一致，设置不可绕过当地限制 | RF 参数与硬件清单、产测/地区配置和恢复后回归 |
| SW-EX09 内容与许可证 | 逐核心及程序、字体/主题/素材/演示内容记录来源/版本/区域范围 | 分地区软件/内容清单、所需源码与许可交付，无未知捆绑组件 |
| SW-EX10 售后可用性 | 英文与目标国语言恢复/存档说明、公开下载与校验、硬件 ID 匹配及过期链接维护 | 第二人在目标地区网络/语言条件下完成恢复，不依赖开发者私人网盘 |

先建立可工作的本地镜像恢复，再决定是否需要 OTA；不因添加海外需求就无条件自研云服务。若增加账号、遥测、联网刮削或 AI 功能，另评估个人数据、服务可用性、内容来源、费用和安全维护，不能作为默认隐藏依赖。

### 11.3 海外安全责任不是“等 2027 再处理”

[欧委会 CRA 摘要](https://digital-strategy.ec.europa.eu/en/policies/cra-summary)给出的时间为：适用报告义务自 2026-09-11 开始，主要规定自 2027-12-11 全面适用。是否属于其范围必须依据具体直接/间接网络连接能力等评估，不能以“离线菜单”自动排除。已在售/历史产品和新投放产品的过渡也应分别确认。

对特定无线型号还需评估 RED 网络安全的现行要求及 2027 年过渡；[2026/339](https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=CELEX%3A32026R0339)的撤销生效点是 2027-12-11，不能误写成 2026 年已立即取消。英国 PSTI 的适用/例外另评估。实际任务、负责人及官方入口在 10 手册第 13 节统一管理；本文未声称已完成符合性评估。
